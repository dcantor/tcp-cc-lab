17. Walkthrough K — is BBR better on long fat networks?

The claim to test: on paths with high bandwidth and high latency, BBR delivers more throughput than the loss-based algorithms. This section tests it as a controlled comparison: one variable (the algorithm), everything else held identical and verified, and the path conditions under which the claim should and should not hold, chosen before the run.

Design

elementchoice
QuestionDoes the congestion control algorithm change the throughput of a single bulk TCP flow on a high-bandwidth, high-latency path, and under which path conditions?
Treatment (what varies)The sender's congestion control: CUBIC, BBR (v1) or Reno. Each is a separate host (a-cubic, a-bbr, a-reno) sending to its own peer across the same routers, emulator and bottleneck.
Path conditions (factors)Bottleneck 500 Mbit/s; RTT 10 ms (a short-path reference), 100 ms and 150 ms; four path types: clean (1 × BDP buffer, no loss), shallow buffer (¼ × BDP), 0.01 % random loss and 0.1 % random loss (1 × BDP). 3 × 4 = {{kmeta:cells}} cells.
Controlled (identical for all three)Everything on the hosts: the same image, kernel, every TCP and socket sysctl (section 4), MTU 1500, fq on eth1, iperf3 version and options. Nothing on the hosts was changed for the experiment. Only one flow at a time crosses the bottleneck.
TrafficOne TCP flow at a time across the bottleneck: iperf3 -c <peer> -p 5201 -t {{kmeta:duration}} -b {{kmeta:bitrate}}, a single stream (no -P) for {{kmeta:duration}} s with the application offering {{kmeta:bitrate}}bit/s, from a-<algorithm> to b-<algorithm>.
ReplicationOne run per algorithm per profile: {{kmeta:runs}} runs in all, about {{kmeta:minutes}} minutes.
OrderWithin each profile the three algorithms run back to back in a random order (seeded, seed {{kmeta:seed}}), 2 s apart.
MeasurementReceiver-side goodput reported by iperf3 over the whole run (start-up included); also retransmits, smoothed RTT, bottleneck drops and the sender's TCP memory-pressure events.
AnalysisPer profile: each algorithm's goodput, and BBR's as a ratio of CUBIC's and Reno's. With one run per profile there is no within-profile variance to test against, so differences under ~5 % (the run-to-run spread seen in sections 16 and 20) count as no difference.
Integrity checksBefore and after the experiment every host's TCP and socket sysctls, eth1 MTU and qdisc were fingerprinted (SHA-256 over 121 settings). Before: all six hosts identical apart from the algorithm: {{kmeta:same}} (fingerprint {{kmeta:hash}}). After: unchanged: {{kmeta:unchanged}}. Every run's reported algorithm matched its host; failed runs: {{kmeta:errors}}.

Hypotheses, written down before the run:

  • H1 — clean path: no meaningful difference. With no loss and a 1 × BDP buffer every algorithm can fill the pipe (section 16), so BBR should not win.
  • H2 — random loss: BBR is much faster, and the gap grows with RTT. A loss-based sender halves (Reno) or cuts by 30 % (CUBIC) its window on every loss, and on a long path it needs many round trips to grow back; BBR does not treat an isolated loss as congestion.
  • H3 — shallow buffer: BBR is faster on long paths. With a buffer smaller than the BDP, a loss-based sender's sawtooth falls below the pipe size after every overflow; BBR paces at the measured bottleneck rate and does not need the buffer.

Threats to validity

  • Emulated loss is random and independent. Real loss is often bursty or caused by congestion elsewhere. Random loss is exactly the case where BBR's design helps most, so H2 is the most favourable test for BBR; the clean and shallow-buffer cells are the fairer comparison.
  • One flow at a time. This is a throughput test for a single transfer. When BBR shares a link with CUBIC or Reno it takes far more than its fair share (sections 9 and 14). Being "better" for your own transfer and being a good neighbour are different questions.
  • BBR v1. Linux 6.12 ships BBR v1. BBRv3 reacts to loss above about 2 %, retransmits less, and would give smaller gains in the loss cells.
  • Small host VMs. The hosts' TCP memory limit (section 4) is the same for every algorithm, and pressure events are reported in the cost table. It caps what any algorithm can reach on the longest paths, so it narrows the differences rather than creating them.
  • One run per profile. Large effects (several times the throughput) are far outside run-to-run noise; small ones (a few %) are not, and the text does not claim them.
  • 30 s runs include start-up. At 150 ms slow start takes a few seconds of each run, the same for every algorithm. Longer transfers would bring the averages closer to the steady-state rates.
